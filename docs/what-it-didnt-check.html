On building a spreadsheet auditor

Your spreadsheet auditor should tell you what it didn't check

Tools that check spreadsheets either compute nothing or claim to compute everything. Both let you believe more was verified than was. There is a third option, and it costs you a number you may not want to see.

A hardcoded VAT rate sat in one cell of a client invoice sheet for two years. The column around it was formulas. The number it produced was plausible. Nobody saw it, because there was nothing to see — no red, no #VALUE!, no broken link. Somebody had typed over one cell in 2023 and the sheet had looked perfectly healthy ever since.

That is the shape of nearly every expensive spreadsheet error: not a formula that fails, but one that quietly stops being a formula.

Two ways to look for it, both of them partial

A tool auditing that workbook has two established options. It can read the formulas as structure — parse them, never compute them — and find the shape problems: a constant in a run of formulas, a SUM that stops one row short of its data, a total that sweeps up a subtotal of its own rows. These are real findings and they need no arithmetic at all.

Or it can evaluate: reimplement enough of Excel to recompute the sheet and compare. Two Python libraries have worked at this for years and both still have gaps, which is the first clue about how large the job is.

The structural tool will tell you nothing about whether the arithmetic is right. The evaluating tool will tell you about the arithmetic it managed, and typically will not tell you which parts those were. Both hand you a report that reads like a verdict on the whole workbook.

Why full evaluation is a trap

Not "a lot of work" — a different product. Implementing Excel semantics means, at minimum:

  • 500-odd worksheet functions, each with its own argument coercion.
  • Coercion rules specific to Excel — empty string against zero, TRUE as 1, text promoted to number in some argument positions and not others.
  • Nine error types with per-function propagation. #N/A passes through IFERROR differently from #VALUE!.
  • Dates, including the 1900 leap-year bug Excel deliberately preserves for Lotus compatibility, and the 1900/1904 workbook setting that shifts every date by four years.
  • Floating point as Excel presents it — IEEE 754 doubles displayed at fifteen significant figures, with special-cased cosmetic correction so that =0.1+0.2-0.3 shows zero.
  • Both array systems: legacy Ctrl-Shift-Enter arrays and modern dynamic-array spill.
  • Locale. Function names and argument separators differ by install language.
  • Calculation settings: iterative calculation, precision-as-displayed.

But the size is not the trap. The trap is partial coverage. Evaluate eighty per cent of a workbook, stay quiet about the rest, and no reader can tell which numbers were checked. The report looks the same either way.

And there is a worse failure hiding behind it. One coercion bug makes the tool report a discrepancy on a correct workbook. A tool that cries wolf on correct work loses trust faster than one that misses things — because the first wrong alarm is the last time anyone reads the output carefully.

The third option

Recompute a small, closed subset. Refuse everything else by name. Then publish the ratio.

In Tickmark, the tool I have been building, that subset is the arithmetic operators plus SUM, AVERAGE, MIN, MAX, COUNT, COUNTA, ROUND, ROUNDUP, ROUNDDOWN and ABS, over cells holding numbers. A formula that reaches outside it — a VLOOKUP, an IF, a date, a cell holding text — is declined and counted, never approximated. Every audit ends with a line like this one, which is the real figure from the sample report linked at the foot of this page:

✓ recomputed 37 of 41 formulas
4 fell outside the evaluated subset
An unverified formula has not been checked. It is not a formula that passed.

That second number is the one doing the work. It is also the number a marketing department would ask you to remove.

What "refuse" has to mean in practice

A closed subset sounds simple until you write it. Four decisions that turned out to matter more than the function list:

Round away from zero, not to even. Python's round(2.5) is 2. Excel's ROUND(2.5,0) is 3. Shipping the language default would have reported a discrepancy on a correct workbook every single time a value landed exactly on a half — the exact false alarm the whole design is meant to avoid.

Follow Excel's documented range rule; refuse its undocumented scalar one. =SUM(A1:A3) with text in A2 sums the two numbers — that is documented behaviour, safe to implement, and it is what makes the verified count worth having. =SUM(1,"2") coerces by a different rule, and that rule is precisely the kind of subtlety that produces wrong answers on right workbooks. It is declined.

An aggregate over nothing numeric is refused, not answered. Excel says SUM of an empty range is zero, and that is true. But in an audit, a range that yielded nothing far more often means the cells could not be read than that somebody totalled emptiness — and a confident zero against a real stored figure is a false alarm with a very convincing face.

Compare with a relative tolerance, near 1e-9. Too tight and ordinary float noise reads as a discrepancy on correct work. Too loose and a real error slips through. This is a genuine judgement, not a free parameter.

Refusing is the feature

Every one of those decisions makes the verified count smaller. That is the point. The number is only worth printing because the refusals are honest — a tool that quietly guesses reports a bigger figure and a worthless one.

There is a real temptation to grow the list. Someone asks for IF, then VLOOKUP, then date arithmetic, and each one is individually reasonable. That road ends at a spreadsheet engine that is wrong in ways nobody can predict. The closedness is the discipline; the function list is just where it currently sits.

What the honesty buys you

One finding that no structural check can reach: a stored value that contradicts its own formula. Somebody set calculation to manual, an input changed, the sheet was never recalculated, and the file went out with figures that do not match the formulas beside them. There is no cycle, no error, no shape inconsistency. The only evidence is that the stored number and the computed number differ — and you cannot see that without computing one of them.

A narrow evaluator finds it. A narrow evaluator that tells you its own limits lets you trust the finding.
